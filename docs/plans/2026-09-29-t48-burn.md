# T48 burn from the dashboard, armed by a hold (2026-09-29)

**Spec:** the owner's decision in the 2026-09-29 session, which overrides `docs/phase2-handoff.md`'s "No burn
anywhere in gatbox-web" and hard rule 6. Her approved design:
- a READ / BURN switch in the DUMP tab;
- the image comes from the dump archive or `/srv/gatbox/roms/_images/`;
- the part is exact, and its size must equal the image's;
- a BLANK CHECK must pass;
- **HOLD 3 S TO BURN**, on the Pi's own screen only. It's temporary, until a physical ARM button, which will give the
  same one-time go-ahead;
- then write (minipro verifies), read back twice, and compare with the image;
- the CLI (`gatbox-dump --burn`) has the part name typed to confirm;
- tests use a fake T48 chip.

**Facts read off this Pi (minipro 0.7.4 source + `minipro -d`):**
- `-b`: blank check. Blank: "<name> memory section is blank.", exit 0. Not blank: "Verification failed at address
  0x…: File=0xFF, Device=0x…", exit 1.
- `-w FILE`: write. It erases only if the device can be erased electrically (UV EPROMs can't), then verifies:
  "Verification OK" or "Verification failed at address …" + exit 1.
- The file size must match the device unless `-s` is passed. We never pass `-s`.
- `-d PART` prints "Memory: N Bytes" and "VPP programming voltage: …".

**Global constraints:**
- gatbox-web never touches the T48; `gatbox-dump.service` (user gatbox-dump) does.
- Loopback-only arm.
- No part auto-detect.
- Never write without a blank check that passed in the same job.
- Never pass `-s` or `-y` silently.
- Every burn is logged: `<roms>/burns.jsonl`, one line per burn.
- Repo conventions from CLAUDE.md: TZ=UTC commits, and tests in `tests/`.

## Task 1: fake T48 chip in tests/fake-minipro

- `FAKE_CHIP`: a file holding the chip's contents (UV-erased = all 0xFF).
  - `-r` reads it (instead of `FAKE_ROM`) when set.
  - `-b` passes only if it's all 0xFF, with the real messages.
  - `-w FILE` refuses a size mismatch unless `-s`, "programs" it (bits only go 1→0, like an EPROM), then prints
    "Verification OK" or "Verification failed at address …".
  - `FAKE_WRITE_FAIL=1` leaves one byte wrong.
- `-d PART` prints "Memory: N Bytes" from `FAKE_SIZES` (part=bytes pairs; default 262144 for the 27C020s, 131072 for
  27C010), plus a "VPP programming voltage: 12.5V" line.
- Tests (in Task 2's run): the fake's behaviour is covered through gatbox-dump's burn tests.

## Task 2: burn core in tools/gatbox-dump (class Burn) + CLI

- `Burn(image, part, machine, arm=None, say, status)`. `run()` does, in order:
  1. the image is readable and is a file (not a directory, no `..`);
  2. `-d PART` size == image size, else Stop "the image is N bytes, PART holds M";
  3. the non-JEDEC check (as Dump);
  4. the pin check (as Dump);
  5. the blank check (`-b`), else Stop "not blank: UV-erase it first";
  6. the arm check (job mode): `armed.until >= now`, else Stop "the arm expired: hold again";
  7. write (`-w image`; no `-s`, no `-y`, no `-v`); minipro's "Verification OK" is required;
  8. two reads compared with the image's SHA-1;
  9. result: `burned: {image, sha1, part, vpp, verified: true}`.
- Burn log: `<roms>/burns.jsonl` (append, one line per burn, stopped ones too).
- CLI: `gatbox-dump --burn IMAGE -p PART [-m SLUG] [--yes]`. It runs the pin check and blank check, prints the image
  (size, SHA-1, the archive's MAME identity when the sidecar has it) and the part (size, VPP), asks for the part name
  to be typed, then writes and verifies. `--json` isn't offered for burn.
- An ID complaint at write → the same `id_stop` hints.
- Tests (tests/test-dump.py, new section "burn"):
  - a size mismatch stops before the chip is touched;
  - not blank → stopped, chip unchanged;
  - burned + verified, chip == image;
  - a write failure → stopped ("Verification failed");
  - a readback mismatch → stopped;
  - a mistyped part name in the CLI → no write;
  - non-JEDEC needs `--yes`;
  - the burns.jsonl line;
  - an ID mismatch stops with the hint.
- Command: `bash tests/test-dump.sh`. Commit.

## Task 3: job mode for burn + blank-only jobs

- `run_job` dispatches on `req["op"]`:
  - `"dump"` (default, as now);
  - `"blank"`: pin + size + blank check only, result `{op: "blank", blank_ok, part, image, sha1}`;
  - `"burn"`: needs `req["armed"] = {"by", "at", "until"}`. A missing or expired arm → stopped, nothing written.
- Status/steps as for dumps; the status carries `op`.
- Tests: job blank OK / not blank; job burn armed → burned; job burn unarmed / expired → stopped, chip unchanged;
  a claimed request never runs twice.
- Command: `bash tests/test-dump.sh`. Commit.

## Task 4: gatbox-web burn API (backend/gatboxweb/dump.py + server.py)

- `GET /api/burn/images`: `.bin` files in the archive's machine folders and in `_images/`, each with machine, size,
  SHA-1 (from the sidecar, else computed, cached by stat) and romident. The listing is `realpath`-confined to ROMS.
- `POST /api/burn/blank {image, part}`: validate the image (must be in the listing) and the part (in minipro's list);
  writes request.json with op blank. Same busy/T48 checks as dumps.
- `POST /api/burn {image, part}`: **loopback only (403 otherwise)**. It needs the last status to be op blank, blank_ok,
  the same image and part, finished ≤ 5 min ago (else 409 "blank check first"). It writes request.json with op burn and
  `armed {by: "screen", at, until: at+30}`.
- SSE "dump" events carry burns too (the same status file).
- Tests (tests/test-dump.py web section):
  - the images listing (archive + `_images`, traversal names not listed);
  - blank → request.json op blank;
  - burn from a non-loopback address → 403;
  - burn without a recent blank → 409;
  - burn after a blank OK → request with armed.until ≈ now+30;
  - a mismatched part/image vs the blank → 409.
- Command: `bash tests/test-dump.sh`. Commit.

## Task 5: dashboard BURN mode (web/dash)

- The DUMP tab gets a READ / BURN switch (`.seg`). BURN:
  1. IMAGE: a pick list grouped by machine / `_images`, showing size and MAME match;
  2. PART: the family tiles lit for the image's size, then the exact part as for reads;
  3. BLANK CHECK: the job's result card;
  4. when the blank check passed for this image+part, on the Pi's own screen: **HOLD 3 S TO BURN <image> → <part>**
     (the existing `.hold` pattern; on a phone: "arm it at the Pi");
  5. progress, then the VERIFIED / FAILED card.
- A result for the burn names the image and SHA-1 and "2 reads identical to the image".
- Tests (tests/test-dash.py):
  - BURN switch → image list → part → BLANK CHECK (a runner stands in for the path unit, the fake chip blank) → the
    hold appears only locally → hold 3 s → VERIFIED;
  - the phone view shows no hold button.
- Command: `bash tests/test-dash.sh`. Commit.
